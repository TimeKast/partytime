# sk-skins — TimeKast Kit's Swappable Skin System

> **Kit-shipped — grounded in real files:** [`src/app/globals.css`](../../../src/app/globals.css) (the stable layer + the swap point) and `src/app/skins/*.css` (the swappable skins).
>
> **Pair:** [`sk-tokens-neomorphism`](../sk-tokens-neomorphism/SKILL.md) — the per-skin token reference for the neomorphism skin (the active default), tolerant of legacy apps that still ship the `--neo-*` vocab.
>
> **Canonical symbol names:** grep [`project/reference/HOOKS.md`](../../../project/reference/HOOKS.md) before naming any kit-shipped helper in a new file.

> **What this skill is:** the operational SSOT for the swappable skin system. A skin is *one CSS file + a flag* — a complete set of token→value bindings for the 3 themes, swapped in by re-pointing one `@import`. This skill tells you how the swap works, what a valid skin must define, the neutral vocab to write against, and how to opt into a non-default skin. The default skin is **always neomorphism**; for its per-token reference (and for apps still on the legacy `--neo-*` vocab) read `sk-tokens-neomorphism`.

---

## 1. What a skin is — and the two independent axes

A **skin** is the swappable visual identity of the kit: the recipes for surfaces, elevation, color, and radius that make the app *look* a certain way (the kit's default: Neomorphism 2.0). It is **not** the layout, the components, or the theme-switching mechanism — those are stable across every skin.

A skin defines, for **each theme it declares** in `src/config/skins.ts` (a subset of `.light` / `.midnight` / `.dark`), the complete contract token set (§4). Swapping skins = swapping the file that provides those bindings; components never change.

```
stable kit (globals.css + components)  +  one skin file  =  the app's look
                                            └── swap this, nothing else
```

Two orthogonal axes — keep them straight:

| Axis      | Granularity         | When it changes              | Mechanism                                              |
| --------- | ------------------- | ---------------------------- | ------------------------------------------------------ |
| **Theme** | Per-user, runtime   | User toggles light/dark      | `next-themes` sets a class on `<html>` (`.light`/`.midnight`/`.dark`); **which themes are offered is the active skin's choice** — declared in `src/config/skins.ts`, consumed by the provider + toggle |
| **Skin**  | Per-build, the app  | The team picks a skin        | One edit: the `ACTIVE_SKIN` entry in `src/config/skins.ts` (the `globals.css` `@import` is generated from it) (§5) |

> Default to **neomorphism**. The presentation/showcase surfaces and every new app start on it. Switching skins is an explicit, deliberate opt-in (§5), never a side effect of a normal change.

> **Themes are per-skin (registry SSOT).** A skin declares the themes it ships in `src/config/skins.ts` (`SKINS[name].themes`, `defaultTheme`, `system`). A skin need **not** define all three — `neomorphism` ships `light`/`midnight`/`dark`; `fintech` ships only `light`/`dark`. `Providers` and the header toggle derive their theme list, default, and the optional OS-follow "System" option from this registry — never hardcoded in components. The metadata of each theme (es-MX label + Lucide icon) lives in `THEME_META` in the same file.

## 2. The vocab you write against — neutral elevation tokens

Components consume **skin-agnostic** names so the same component renders correctly under any skin. This is the vocabulary the kit ships today:

| Token / class        | What it is                                                       |
| -------------------- | --------------------------------------------------------------- |
| `--elevation-*`      | Elevation/shadow recipe CSS vars (`--elevation-raised`, `--elevation-inset`, `--elevation-pressed`, `--elevation-float`, `--elevation-flat`, + `-sm`/`-lg`/`-hover` size/state variants) |
| `.surface-*`         | Utility classes that apply an elevation recipe + `border: none` (`.surface-raised`, `.surface-inset`, `.surface-pressed`, `.surface-float`, `.surface-flat`, `.surface-interactive`, `.surface-focus`, …) |
| `variant="surface"`  | The Button (CVA) variant name for a surfaced button             |

```tsx
<button className="surface-interactive surface-focus rounded-xl bg-primary px-4 py-2 text-primary-foreground">
  Click me
</button>

<input className="surface-inset surface-focus-inset rounded-xl bg-input px-3 py-2 text-foreground" />
```

The semantic color/surface tokens (`bg-background`, `bg-card`, `text-foreground`, `bg-primary`, …) are the same across skins — only the *values* behind them change per skin. Write semantic aliases, never raw values (§2).

> **Elevation vocabulary:** `raised` / `inset` / `pressed` / `float` / `flat` are the neutral elevation words every skin shares. `raised` is the skin-agnostic word for the default lifted surface. A skin's own internal recipe primitives (e.g. the neomorphism skin's dual light/shadow colors) are **private** to that skin (§4) and never part of what components consume.

> **Legacy apps (pre-v11):** apps generated before the skin system ship the branded `--neo-*` / `.neo-*` / `variant="neo"` vocab instead. That vocab is documented in `sk-tokens-neomorphism` as legacy — it still works, it is the same recipes under a branded name. New code uses `--elevation-*` / `.surface-*` / `variant="surface"`.

## 3. Layers — stable vs. swappable

The kit splits the stable token architecture from each skin's concrete values:

```
┌──────────────────────────────────────────────────────────────────┐
│  src/app/globals.css                            ← STABLE LAYER    │
│  · @import 'tailwindcss'                                          │
│  · @source / @plugin directives                                  │
│  · @theme inline  (Tailwind utility → var() aliases)             │
│  · base styles, scrollbars, safe-area @utilities, animations    │
│  · --toast-bg-* tints (color-mix over the active skin; §4.4)     │
│  · @import './skins/<active-skin>.css';  ← THE SWAP POINT        │
└──────────────────────────────────────────────────────────────────┘
                              │ imports exactly one
                              ▼
┌──────────────────────────────────────────────────────────────────┐
│  src/app/skins/<name>.css                       ← SWAPPABLE LAYER │
│  · the 89 contract vars × 3 themes (§4)                          │
│  · the skin's .surface-* utility classes                        │
│  · any skin-private tokens (§4)                                 │
└──────────────────────────────────────────────────────────────────┘
```

| Belongs in the STABLE layer (`globals.css`)                        | Belongs in a SWAPPABLE skin (`skins/*.css`)              |
| ------------------------------------------------------------------ | -------------------------------------------------------- |
| `@theme inline` aliases (`--color-primary: var(--primary)`, …)     | The raw token values per theme (`--primary: #1e40af`, …) |
| Tailwind directives (`@import`, `@source`, `@plugin`)              | The elevation recipes (`--elevation-raised: …`)          |
| Base/reset CSS, scrollbar styling, safe-area `@utility`, keyframes  | The `.surface-*` utility class definitions               |
| The `@import` of the active skin (the swap point)                 | Skin-private tokens (§4)                                 |
| Derived `--toast-bg-*` tints (skin-agnostic, §4.4)                | Component-contract tokens (`--switch-checked`, `--tab-*`, …) (§4.1) |

> Why the split: runtime theme-swapping (toggle `.light`/`.dark`/`.midnight` on `<html>`) keeps working because the `@theme inline` aliases in the stable layer resolve to whichever theme's vars the active skin defines. Build-time skin-swapping re-binds *which* skin provides those vars. The two axes are independent (§1).

> **Tolerant of un-split apps:** an app generated before the skin split — or the kit itself before its `src/app/skins/` extraction lands — keeps the 3 theme blocks **inline** in `globals.css`, with no `@import './skins/*.css'` line yet. The contract, vocab, and theme selectors above all still hold; only the file layout differs. The swap point (§5) materializes once the skin file is extracted. This skill describes the v11 target architecture and tolerates a `src/` that has not been split yet.

## 4. The contract — what a valid skin must define

> 🔴 A skin is **valid** only when, for **each theme it declares** in `src/config/skins.ts` (`SKINS[name].themes`), it defines the full contract token set, plus the `.surface-*` utility classes. A missing contract var renders components with empty values. The token set is exactly **89 contract vars** (audited against `src/app/skins/*.css`), identical key-set across every theme the skin defines. A skin need **not** define all three theme classes — only the ones it declares (e.g. `fintech` ships `.dark` + `.light`, no `.midnight`); `neomorphism` ships all three.

### 4.1 Contract token groups (89 vars × each declared theme)

| Group                            | Count | Examples                                                                                     |
| -------------------------------- | ----- | -------------------------------------------------------------------------------------------- |
| **Surfaces & color (semantic)**  | 47    | `--background`, `--foreground`, `--card`, `--primary`, `--secondary`, `--muted`, `--accent`, `--border`, `--ring`, `--popover`, `--destructive`, `--sidebar-*`, `--header-*`, `--input-*`, `--table-*`, `--success`/`--error`/`--warning`/`--info`, … |
| **Radius**                       | 1     | `--radius` — el ladder `rounded-*` deriva de este token en el `@theme inline` de `globals.css` (capa estable), anclado en `xl` → ver `sk-tokens-neomorphism §3` |
| **Elevation recipes**            | 9     | `--elevation-raised`, `--elevation-raised-sm`, `--elevation-raised-lg`, `--elevation-raised-hover`, `--elevation-inset`, `--elevation-inset-sm`, `--elevation-pressed`, `--elevation-float`, `--elevation-flat` |
| **Component-contract tokens**    | 8     | `--switch-checked` (switch on-state) · `--tab-list-bg`/`--tab-list-shadow`/`--tab-active-bg`/`--tab-active-fg`/`--tab-active-shadow` (tabs track + active) · `--outline-hover-border` (outline button hover) · `--button-surface-shadow` (primary button on a colored surface) |
| **Legacy shadow aliases**        | 3     | `--shadow-sm`, `--shadow-md`, `--shadow-lg` — **dead/legacy** (§6); not a skin obligation     |
| **Badge colors**                 | 21    | 7 hues × 3 slots (`-bg`/`-text`/`-dot`): purple, blue, slate, emerald, red, amber, pink       |

> 47 + 1 + 9 + 8 + 3 + 21 = **89**. The exact members live in the active skin file `src/app/skins/<name>.css` (the SSOT) — this skill does not duplicate the full enumeration.

> **Why a skin defines the component-contract tokens (not the component):** each resolves a per-skin tension without per-skin logic in the component. The component reads the token; the skin picks the value. Examples: `--switch-checked` is green (`--success`) in neomorphism, cobalt (`--primary`) in fintech; the active tab is an **inset/recessed well** (`--input-bg` + `--elevation-inset`) in neomorphism vs an **accent wash** in fintech; `--button-surface-shadow` is a soft single drop instead of the dual-light extrusion (which halos on a colored surface).

### 4.2 Contract vs. private tokens

A token is **contract** iff a `src/` component (or the `@theme inline` layer) consumes it. A token consumed only inside the skin's own recipes is **private** — other skins are free to omit it.

```
✅ A skin defines private recipe primitives only if its elevation model needs them.
   The neomorphism skin keeps two private light/shadow color primitives its dual-light-source
   recipes are built from (--neo-light / --neo-dark; 0 consumers outside its own .css). A flat
   or glass skin would NOT define them — it has no dual-light-source model.
❌ Treating a skin's private primitives as contract → forces every skin to fake them.
```

> **Private sets differ per skin — count contract, not total declarations.** When auditing a block's `--*` count (§7.2), subtract the skin's private primitives first. Current private sets: neomorphism = 2 (`--neo-light`, `--neo-dark`) → 91 total per theme block; fintech = 5 (`--cobalt-shadow`, `--cobalt-shadow-strong`, `--sidebar-active-shadow`, `--sidebar-active-surface`, `--skin-vignette`) → 94 total. Both resolve to the same **89** contract vars.

### 4.3 🔴 Theme selectors are CLASSES — and `:root` pairs with the skin's defaultTheme

`next-themes` runs with `attribute="class"`: themes toggle by setting a **class** on `<html>`. Every skin defines each theme **it declares** with a **class** selector, and pairs `:root` with the selector of its `defaultTheme` (`config/skins.ts`) — so SSR / first paint / a stale class with no matching block fall back to a valid theme, never to empty tokens.

```css
/* neomorphism — ships all 3; :root paired with the light block */
:root,
.light { /* … contract vars (light) … */ }
.midnight { /* … */ }
.dark { /* … */ }

/* fintech — dark-first, ships only light+dark; :root paired with .dark.
   .light comes AFTER (equal specificity → later rule wins when the `light` class is set). */
:root,
.dark { /* … contract vars (dark / navy) … */ }
.light { /* … */ }
```

```
❌ [data-theme="dark"] / [data-theme="light"]  →  DEAD selector. The kit never sets a
   data-theme attribute (next-themes is attribute="class"), so the rule never matches.
❌ Hardcoding `:root, .light` for every skin → wrong for a dark-first skin (fintech).
✅ Class selectors `.light` / `.midnight` / `.dark` — only the ones the skin declares.
ℹ️  Pair `:root` with the selector of the skin's `defaultTheme`. When an override theme shares
   specificity with the `:root`-paired block, order the paired block FIRST (fintech: `:root, .dark`
   before `.light`). neomorphism keeps the historical `:root, .light` pairing.
```

### 4.4 Derived stable-layer tokens — `--toast-bg-*` (NOT a skin obligation)

Four toast-tint tokens live in the **stable layer** (`src/app/globals.css`, in a `:root` block — *not* in any skin file). They are **derived**, not authored per-skin: each mixes the active skin's semantic status color into `--card`, so a typed toast renders as a **solid tinted card** (opaque), never alpha-over-transparent (which reads black on dark pages or when toasts stack).

```css
/* src/app/globals.css — derived over whatever the active skin defines for --success/--card/… */
--toast-bg-success: color-mix(in oklab, var(--success) 14%, var(--card));
--toast-bg-error:   color-mix(in oklab, var(--error)   14%, var(--card));
--toast-bg-warning: color-mix(in oklab, var(--warning) 16%, var(--card));
--toast-bg-info:    color-mix(in oklab, var(--info)    14%, var(--card));
```

```
✅ Skin-agnostic by derivation: a new skin gets correct toast tints for free — it only defines the
   contract colors (--success/--error/--warning/--info/--card); these four re-resolve automatically.
✅ A skin must NOT redefine --toast-bg-* — they are stable-layer, not part of the 89 contract vars.
🔴 color-mix MUST live in a CSS var here, NOT inline in a class (bg-[color-mix(...)]): Tailwind's
   scanner skips arbitrary values with commas/parens, so the rule is never generated. Consumed as
   bg-(--toast-bg-*) in sonner.tsx. (`default`/typeless toast = info; icons colored per type.)
```

## 5. Opt-in — how to switch the active skin

Switching the active skin is a **single edit** — `ACTIVE_SKIN` in `src/config/skins.ts`:

```ts
export const ACTIVE_SKIN: SkinName = 'neomorphism';   // ← the only switch; change this
```

The `@import './skins/<name>.css'` in `globals.css` is **autogenerated** from `ACTIVE_SKIN` by `pnpm generate:skin` (run automatically in the pre-commit hook). You never hand-edit that line — it sits under a `/* @skin-import */` sentinel and is rewritten to match:

```css
/* src/app/globals.css — the @import below is AUTOGENERATED from ACTIVE_SKIN */
/* @skin-import */
@import './skins/neomorphism.css';
```

To opt into fintech: set `ACTIVE_SKIN = 'fintech'`, then run `pnpm generate:skin` (or just commit — the hook reconciles it).

```
✅ ONE edit: `ACTIVE_SKIN`. The @import is generated — never hand-edited.
✅ Exactly ONE skin @import active at a time (the generator guarantees it).
✅ `tests/unit/skins.test.ts` fails if the @import drifts from `ACTIVE_SKIN` → run `pnpm generate:skin`.
✅ No component / @theme inline edits — the provider + toggle re-derive the theme list from the
   registry, and the @theme inline aliases re-resolve.
✅ A skin is "valid" only when it defines the 89 contract vars for each theme it declares (§4) and
   the .surface-* utility classes; a missing contract var = components render with empty values.
ℹ️  The default is always neomorphism — presentation surfaces and new apps start there.
🔴 Restart `pnpm dev` after switching: Tailwind v4 + Turbopack do NOT hot-reload a changed skin @import.
```

## 6. 🔴 `--shadow-sm/md/lg` status — DEAD/LEGACY

The standard Tailwind v4 `shadow-md` utility does **NOT** read a theme-scoped `--shadow-md` — it inlines Tailwind's hardcoded default (`0 4px 6px -1px …`) and never references `var(--shadow-md)`. So the theme-scoped `--shadow-*` vars are defined-but-unconsumed for the standard utilities: **dead**.

```
✅ A skin does NOT need to define --shadow-sm/md/lg for the standard `shadow-md` utility to
   look right — that utility uses Tailwind's default shadow regardless. They are legacy.
✅ Components that need the SKIN's elevation use the .surface-* utility classes (which consume
   var(--elevation-raised) etc. directly), NOT the standard `shadow-md`.
ℹ️  The live, per-theme path that DOES re-resolve is the arbitrary-value syntax
   shadow-(--elevation-raised) (Tailwind v4 `{util}-(--var)` shorthand): it emits a real var() reference that
   resolves to whichever theme class is active.
```

**Net:** `--shadow-sm/md/lg` stay as harmless dead aliases — they are NOT a skin contract obligation. A new skin is not required to implement them.

## 7. Recipes

### 7.1 Add a new skin

1. Create `src/app/skins/<name>.css`.
2. **Register it** in `src/config/skins.ts` — add a `SKINS` entry `<name>: { themes: [...], defaultTheme, system }`. Declare **only** the themes the skin ships (need not be all 3). `system: true` requires both `light` **and** `dark` (next-themes maps the OS to those).
3. Define the full **89** contract vars (§4.1) for **each declared theme**, with class selectors (§4.3), pairing `:root` with the `defaultTheme` block.
4. Define the `.surface-*` utility classes.
5. Keep any skin-private recipe primitives internal — do not expose them as contract (§4.2).
6. Do **not** rely on the standard `shadow-md` utility for skin elevation (§6) — use `.surface-*` / `shadow-(--elevation-*)`.
7. Activate (§5): set `ACTIVE_SKIN = '<name>'` and run `pnpm generate:skin` (the pre-commit hook also does it) — the `globals.css` `@import` regenerates. Icons/labels come from `THEME_META`; no component edits. `tests/unit/skins.test.ts` validates the wiring.

### 7.2 Audit a skin

Run the §8 checklist. Quick checks:

- Confirm the theme blocks present match `SKINS[name].themes` in `config/skins.ts` — no more, no fewer (`tests/unit/skins.test.ts` automates this).
- Count the `--*` declarations per theme block — the 89 contract vars must be present in **each declared theme** (private primitives are extra, allowed — §4.2: neomorphism +2 → 91 total, fintech +5 → 94 total).
- Confirm the selectors are classes (`.light` / `.midnight` / `.dark`) with `:root` paired to the `defaultTheme` block — no `[data-theme]`.
- Confirm component code consumes `--elevation-*` / `.surface-*`, not raw `box-shadow` recipes or the standard `shadow-md`.

### 7.3 Switch the active skin

Re-point the one `@import` in `globals.css` (§5). No component edits. Verify every declared theme still renders coherently after the swap.

### 7.4 Keep Oxide out of markdown — the `@source not` lines in `globals.css`

Tailwind v4's Oxide scanner reads **every non-gitignored file** for class-looking strings. Real incident in this kit: a markdown file with a malformed CSS example inside backticks crashed Turbopack with `"Unexpected end of input"` and every route returned 500. The guard is the header of `src/app/globals.css`:

```css
@import 'tailwindcss';
@source '../../src/config'; /* positive — force-scan label/permission strings */
@source not '../../docs'; /* markdown with CSS in backticks */
@source not '../../.agent'; /* legacy dir — no-op if absent */
@source not '../../project'; /* planning / backlog markdown */
```

- Paths are relative to `globals.css`, not to the repo root (`../../` = root). Keep them **after** `@import 'tailwindcss'`.
- `@source not` on a directory that does not exist is a no-op — safe to keep preemptively.
- New directory with markdown that embeds CSS (a docs tree, a proposals tree) → add its `@source not` line **before** the first dev-server crash, not after.
- Symptom to recognize: a 500 on every route right after editing a `.md` file → check `@source not` coverage first.

## 8. Anti-patterns

| ❌                                                                | ✅                                                                       |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Two active `@import './skins/*.css'` at once                     | Exactly one active skin import (§5)                                      |
| Hand-editing the `globals.css` skin `@import`                    | Edit `ACTIVE_SKIN`; the `@import` is generated by `pnpm generate:skin` (§5) |
| Hardcoding the theme list in a component / assuming 3 themes      | Derive from `config/skins.ts` (`activeSkinThemes()`) (§1)               |
| A skin defining only some of the 89 contract vars per theme      | Full contract set × **each declared theme** (§4.1)                      |
| `[data-theme="dark"]` selectors, or hardcoding `:root, .light`   | Class selectors for declared themes; `:root` paired with `defaultTheme` (§4.3) |
| Editing a component to "make a skin work"                        | Components are skin-agnostic; only the skin file changes                 |
| Relying on standard `shadow-md` for skin elevation               | `.surface-*` / `shadow-(--elevation-*)` (§6)                            |
| Exposing a skin's private recipe primitives as contract          | Keep them internal to the skin (§4.2)                                    |
| Raw hex / `box-shadow` recipe inline in a component              | Semantic alias + `.surface-*` (§2)                                      |

## 9. Checklist — authoring or auditing a skin

- [ ] Registered in `src/config/skins.ts` (`SKINS` entry: `themes`, `defaultTheme`, `system`) (§1)
- [ ] Defines all **89** contract vars (§4.1) for **each declared theme**
- [ ] Class selectors for declared themes; `:root` paired with the `defaultTheme` block — no `[data-theme]`, not hardcoded to `.light` (§4.3)
- [ ] Defines the `.surface-*` utility classes
- [ ] Skin-private recipe primitives kept internal, not leaked as contract (§4.2)
- [ ] Does **not** rely on the standard `shadow-md` utility for skin elevation (§6)
- [ ] Activated by editing `ACTIVE_SKIN` (the `globals.css` `@import` is generated via `pnpm generate:skin`) (§5)
- [ ] `system: true` only if both `light` and `dark` are declared
- [ ] Each declared theme renders coherently after a swap
