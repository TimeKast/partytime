## 1. Table System

The table system has three layers, plus an escape hatch for what they don't cover:

| Layer                    | Entry point                     | Best for                                 |
| ------------------------ | ------------------------------- | ---------------------------------------- |
| **"Batteries included"** | `DataTable`                     | 90% of tables — built-in search + paging |
| **Composable**           | `Table` + `useTableState`       | External filter bars, custom toolbars    |
| **Server-driven**        | `Table` + `useServerTableState` | 100+ rows, URL-synced filters            |
| **Escape hatch** (not kit-wrapped) | `@tanstack/react-table`, imported directly | Grids needing what the layers above don't do — §1.6 |

### 1.1 `DataTable`

```ts
import { DataTable } from '@/components/ui/data-table';
// src/components/ui/data-table.tsx (renders Table + TableSearch + TablePagination)

interface DataTableProps<T extends object> {
  data: T[];
  columns: TableColumn<T>[];
  keyExtractor: (row: T) => string | number;
  searchableColumns?: (keyof T)[];
  searchPlaceholder?: string; // Default: 'Buscar...'
  pageSize?: number; // Default: 10
  showSearch?: boolean; // Default: true
  showPagination?: boolean; // Default: true
  alwaysShowPagination?: boolean;
  emptyMessage?: string; // Default: 'No hay datos para mostrar'
  emptyIcon?: React.ComponentType<SVGProps>;
  emptyAction?: { label: string; onClick: () => void };
  title?: string;
  description?: string;
  actions?: React.ReactNode;
  onRowClick?: (row: T) => void; // table view only
  view?: 'table' | 'cards'; // Default: 'table'
  renderCard?: (row: T) => React.ReactNode; // required for view="cards"
  className?: string;
}
```

```tsx
<DataTable
  data={users}
  columns={[
    { id: 'name', header: 'Nombre', accessor: 'name', sortable: true },
    { id: 'email', header: 'Email', accessor: 'email' },
    { id: 'role', header: 'Rol', accessor: (row) => <Badge>{row.role}</Badge> },
  ]}
  keyExtractor={(row) => row.id}
  searchableColumns={['name', 'email']}
  pageSize={20}
  title="Usuarios"
  actions={
    <Button onClick={onAdd}>
      <Plus /> Agregar
    </Button>
  }
/>
```

Use individual components (`Table` + `useTableState`) when you need external filter bars or server-side pagination.

#### Card view — "Tarjetas / Tabla"

For collections where each row has its own identity (clients, projects, agents), `DataTable` can render the page as a grid of cards (1 → 2 → 3 columns from 375px). **Search, sort order and pagination are the same in both views** — only the rendering of the page changes. Admin lists that are dense and comparative (users, audit log) stay a table: don't add the switch just because it exists.

```tsx
import { CollectionViewToggle } from '@/components/common/CollectionViewToggle';
import { useCollectionView } from '@/lib/hooks/useCollectionView';

const { view, setView } = useCollectionView({ storageKey: 'clientes', defaultView: 'cards' });

<CollectionViewToggle value={view} onChange={setView} />
<DataTable
  data={clients}
  columns={columns}
  keyExtractor={(c) => c.id}
  view={view}
  renderCard={(c) => <ClientCard client={c} />}
/>
```

- **View resolution** (`useCollectionView`): `?vista=tarjetas|tabla` in the URL → the viewer's last choice on that screen (`localStorage`, per `storageKey`) → `defaultView`. Choosing writes both, the URL with `router.replace`. It reads `useSearchParams`, so a statically rendered route wraps the screen in `<Suspense>`; protected pages render per request and need nothing.
- **The card owns its interaction:** `onRowClick` applies to table rows only. Compact card: the name as a stretched link to the detail, ≤4 signals (status, one or two key fields), no nested cards.
- `view="cards"` without `renderCard` falls back to the table.

### 1.5 Hooks — `useTableState` vs `useServerTableState`

| Hook                  | Data size | State lives in | Best for                           |
| --------------------- | --------- | -------------- | ---------------------------------- |
| `useTableState`       | <100 rows | Client memory  | Catalogs, inline editing           |
| `useServerTableState` | 100+ rows | URL params     | Logs, transactions, shareable URLs |

```tsx
import { useTableState } from '@/lib/hooks/useTableState';

const { paginatedData, onSort, getSortDirection, setSearch, page, totalPages, setPage } =
  useTableState({
    data: products,
    searchableColumns: ['name', 'sku'],
    pageSize: 20,
  });
```

```tsx
import {
  useServerTableState,
  PAGE_SIZE_OPTIONS,
  DEFAULT_PAGE_SIZE,
  MAX_PAGE_SIZE,
} from '@/lib/hooks/useServerTableState';

const { sort, dir, page, limit, setSort, setPage, setPageSize, getSortDirection } =
  useServerTableState({ defaultLimit: DEFAULT_PAGE_SIZE });
// URL: ?sort=name&dir=asc&page=2&limit=20
```

> `useServerTableState` re-exports `PAGE_SIZE_OPTIONS`, `DEFAULT_PAGE_SIZE`, `MAX_PAGE_SIZE` from `@/lib/db/utils/pagination` so client + server share constants. Pair with server-side fetch using `@/lib/db/utils/pagination` (see [`sk-db`](../sk-db/SKILL.md)).

**Sort cycle:** Header click cycles `null` (↕️) → `asc` (↑) → `desc` (↓) → back to `null`.

**Cascading filters (SK.md §3.1 — mandatory with 2+ filters):** Each filter computes its options from the subset already filtered by the OTHER filters — never a static option list next to a live dataset (a hardcoded `ROLE_OPTIONS` shows roles that no surviving row has, and hides the ones that appear later). For each filter: take the rows that pass every *other* filter, then `unique(rows.map(r => r.field))`. Only disable cascading when the issue declares it explicitly (e.g. `static filter options — see AC-3`).

### 1.6 When to drop down to `@tanstack/react-table`

Reach for the three layers above first — that is the intended path for essentially every table in a kit app. `DataTable` is the default: search and pagination are built in, and it takes no configuration beyond `data` / `columns` / `keyExtractor`. When the toolbar or the paging has to live outside the table, `Table` + `useTableState` / `useServerTableState` (§1.5) already covers it.

The kit ships `@tanstack/react-table` as a stack default, so in a fresh app it is already there — but check `package.json` before you count on it, never assume (a derived project's manifest is born frozen and diverges). What the kit does **not** ship is a wrapper over it: no component, no hook, no preset on top, so importing the package directly (`import { useReactTable } from '@tanstack/react-table'`) is the entry point. It is headless: it gives you table state and no markup, so the rendering, the empty state and the pagination controls are yours to compose.

Use it only when the grid needs behaviour the kit's table does not implement — column resizing and pivoting/grouping are the usual candidates, but treat that as examples, not a closed list: the kit does not validate feature-by-feature parity, so decide case by case against §1.1–§1.5 and stay on the kit's table when it already fits. Row virtualization is **not** on that list: the table library is headless and does not virtualize, so it needs a virtualization library the kit does not ship — that install is a decision of its own (`CODING.md §7`).

Dropping down widens what you compose; it does not narrow what the kit requires of the result. Cascading filters stay mandatory with 2+ filters (`SK.md §3.1`), the grid is still mobile-first from 375px (`SK.md §3.2`), and rows still show human IDs, never UUIDs (§8). The component you compose lives in `common/` or its feature folder — **never** in `components/ui/` (`SK.md §3.3`).

> Charts follow the same shape — `recharts` is shipped and unwrapped too. See [`sk-features-index`](../sk-features-index/SKILL.md) §Core Features and [`kb-dataviz`](../kb-dataviz/SKILL.md).

## 2. Form System — `@/components/form` (NOT shadcn)

> 🔴 **This repo does NOT ship shadcn's `form.tsx`.** There is no `@/components/ui/form`. Use the kit at `@/components/form/*` — it wraps `react-hook-form` + Zod with a zero-boilerplate API.

### 2.1 `Form` + `useForm`

```ts
import { Form, useForm } from '@/components/form';
// src/components/form/Form.tsx — passes `isSubmitting` down via context

interface UseFormOptions<T extends FieldValues> {
  schema: z.ZodType<T>; // Zod schema — NO resolver needed
  defaultValues?: DefaultValues<T>;
  mode?: 'onBlur' | 'onChange' | 'onSubmit' | 'all'; // Default: 'onBlur'
}

interface FormProps<T extends FieldValues> {
  form: UseFormReturn<T>;
  onSubmit: (data: T) => Promise<void> | void;
  children: React.ReactNode;
  className?: string;
}
```

```tsx
'use client';
import { z } from 'zod';
import { Form, FormField, SubmitButton, useForm } from '@/components/form';
import { toast } from 'sonner';

const schema = z.object({
  email: z.string().email('Email inválido'),
  name: z.string().min(2, 'Mínimo 2 caracteres'),
});
type FormData = z.infer<typeof schema>;

export function UserForm({ onSubmit }: { onSubmit: (data: FormData) => Promise<void> }) {
  const form = useForm({ schema, defaultValues: { email: '', name: '' } });

  return (
    <Form
      form={form}
      onSubmit={async (data) => {
        try {
          await onSubmit(data);
          toast.success('Usuario guardado');
        } catch (err) {
          console.error('UserForm submit failed:', err);
          toast.error('No pudimos guardar. Intenta de nuevo.');
        }
      }}
      className="space-y-4"
    >
      <FormField name="email" label="Email" type="email" autoComplete="email" />
      <FormField name="name" label="Nombre" />
      <SubmitButton>Guardar</SubmitButton>
    </Form>
  );
}
```

**Notes:**

- `useForm` takes `{ schema, defaultValues?, mode? }` — NOT `react-hook-form`'s signature. No `resolver` — Zod is wired internally.
- `FormField` reads `register()` from `FormProvider` via `useFormContext()`. No `control` prop, no render props.
- Server-action integration: call the action inside `onSubmit`, destructure `ActionResult<T>` (see [`sk-api`](../sk-api/SKILL.md) §2), `toast.error(result.error)` on failure.

### 2.7 Unsaved-changes guard + save-in-flight

**Con el wrapper `<Form>` el guard es automático.** `<Form>` auto-registra el estado dirty en el guard global (prompt al navegar + protección del self-heal del PWA) y expone los helpers vía `useFormContext()`:

```tsx
import { useFormContext } from '@/components/form'; // NO el de react-hook-form

const { confirmNavigation } = useFormContext();

// Cancel (botón programático — el guard NO intercepta router.push solo):
<Button type="button" onClick={() => confirmNavigation(() => router.push('/users'))}>Cancelar</Button>

// Redirect post-submit exitoso: router.push DIRECTO (push programático no dispara prompt):
router.push('/users');
```

Opt-out para forms efímeros / filtros: `<Form guardUnsaved={false}>`.

**Forms con react-hook-form crudo** (sin `<Form>`) llaman el hook explícito:

```ts
import { useUnsavedChangesGuard } from '@/lib/hooks/useUnsavedChangesGuard';
const { confirmNavigation } = useUnsavedChangesGuard({ isDirty, disabled: isSubmitting });
```

Cubre: clicks en `<a>` (`ConfirmDialog`), cierre/reload de tab (`beforeunload`), back/forward (native confirm). **NO** intercepta `router.push()` programático — por eso el Cancel necesita `confirmNavigation` y el redirect post-submit no necesita helper.

**`useSaveInFlight` — la 2ª señal de "trabajo en riesgo"** para pantallas con autosave / mutación optimista / server action en vuelo (sin form dirty):

```ts
import { useSaveInFlight } from '@/lib/pwa';
useSaveInFlight(status === 'saving' || status === 'dirty'); // leak-proof: limpia en unmount
```

El self-heal del PWA no recarga mientras haya un save en vuelo. Detalle → [`sk-pwa`](../sk-pwa/SKILL.md).

### 3.2 `BreadcrumbSetter` — dynamic segment labels

When a page has a dynamic param (UUID), resolve the label server-side and push to breadcrumb context:

```tsx
import { BreadcrumbSetter } from '@/components/common/BreadcrumbSetter';

export default async function UserPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const user = await getUser(id);

  return (
    <>
      <BreadcrumbSetter segment={id} label={user.name} />
      <h1>{user.name}</h1>
    </>
  );
}
```

Result: `Users > John Doe` instead of `Users > abc-123-uuid`.

**Rules:** one setter per dynamic segment, renders null (side-effect only), always used on pages with `[id]`-style params.

## 4. Feedback & Dialogs

> **Cross-platform note:** Radix primitives that activate modal scroll-lock / `RemoveScroll` trigger `react-remove-scroll-bar` and tag `<body>` with `data-scroll-locked`. In this section: `AlertDialog` (always modal), `Dialog`/`Sheet` (modal default), `Popover` only with `modal=true`. Add to that `DropdownMenu` (§6.4, modal default) and any Radix `Select` via `FormSelect` (§2.3, uses `RemoveScroll` in its content unconditionally — no `modal` prop). The kit ships an override in `globals.css` (`html body[data-scroll-locked] { margin-right: 0 !important; … }`) that neutralizes the library's `margin-right` compensation on Windows/Linux — without it, opening any of them shifts the viewport ~15px. Don't remove it. Detail → §11.4.

### 4.5 Popover vs DropdownMenu — decisión

Both are Radix primitives that float content over the page. They are **not interchangeable**. Picking the wrong one leaks bugs into derived projects (transparent panels, doesn't close, conflicts with other portals, broken a11y).

**Decision rule:**

- ¿El usuario navega con flechas para elegir UNA acción/opción? → `DropdownMenu`
- ¿El contenido es estructurado (lista scrolleable + header + footer / form / preview / live data)? → `Popover`

**Ejemplo canónico — `src/components/layout/Header.tsx` shippea los 3 casos juntos:**

| Componente        | Primitiva      | Por qué                                                                                                  |
| ----------------- | -------------- | -------------------------------------------------------------------------------------------------------- |
| Avatar menu       | `DropdownMenu` | Acciones a ejecutar (Editar perfil, Cerrar sesión) — `role="menu"` + flechas + cierre al click correctos |
| Theme toggle      | `DropdownMenu` | Selección entre 3 opciones excluyentes — comportamiento de menú radio                                    |
| Notification bell | `Popover`      | Contenido scrolleable con header/footer + items que abren un Dialog — no es menú                         |

**Por qué la distinción importa:**

- `DropdownMenu` agrega `role="menu"` + `role="menuitem"` y cierra al click por default. Forzarlo en contenido estructurado obliga a `e.preventDefault()` en cada botón inline (mark-as-read, links del footer) y rompe la semántica para screen readers.
- `Popover` es contenido genérico — no asume nada del layout interno. Posicionamiento + portal + outside-click + escape gratis, sin las suposiciones de menú.

**🔴 NO rodar tu propio dropdown con `useState` + `useRef` + click-outside listener.** El bell antiguo lo hacía y generó 3 bugs recurrentes en derivados: transparente cuando un wrapper redefine `--background`, no cerraba bien al abrir el detail Dialog (cualquier click dentro del portal externo disparaba close), y se clipeaba con ancestros `overflow:hidden`. Radix Portal resuelve los tres en una primitiva.

```tsx
import { Popover, PopoverContent, PopoverTrigger } from '@/components/ui/popover';

<Popover open={open} onOpenChange={setOpen}>
  <PopoverTrigger asChild>
    <MyTriggerButton />
  </PopoverTrigger>
  <PopoverContent align="end" sideOffset={8} className="w-80 p-0">
    {/* contenido libre — header, lista, footer, form, etc */}
  </PopoverContent>
</Popover>;
```

> Trigger custom debe ser `forwardRef` con spread de props para que Radix le inyecte `ref`, `aria-expanded`, `data-state` (ver `NotificationBell.tsx` como referencia).

## 11. Responsive recipes (mobile-first 375px — `SK.md §3.2`)

Every screen must be 100 % usable at 375px without horizontal scroll. These are the layout situations that come up in every kit project, written against what the kit ships.

### 11.1 Shell container — no horizontal overflow

`DashboardShell` (§6.1, `src/app/(protected)/DashboardShell.tsx`) already wraps the protected area with this shape; a custom shell must keep it:

```tsx
<main className="pt-content-safe pb-content-safe min-w-0 lg:ml-60 lg:pb-0">
  <div className="max-w-full p-4 lg:p-6">{children}</div>
</main>
```

| Class                | Why it matters                                                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `min-w-0`            | Flex/grid children can shrink below their intrinsic min-content                                                                  |
| `max-w-full`         | Hard cap at 100 % of the parent — prevents overflow from children                                                                 |
| `p-4 lg:p-6`         | Consistent padding that scales up on desktop                                                                                     |
| `pt-content-safe`    | Clears the fixed header **plus** the iOS safe area (`--header-height + env(safe-area-inset-top)`, `globals.css` `@utility`) — never a hardcoded `pt-16`, which ignores both |
| `pb-content-safe` / `lg:pb-0` | Clears the mobile `BottomNav` plus the bottom safe area; desktop has no bottom nav                                       |
| `lg:ml-60`           | Left offset for the desktop sidebar (collapses on mobile)                                                                        |

**Rule:** any flex/grid child that must shrink (table cells, tab labels) needs `min-w-0` too — without it, `truncate` overflows its parent.

### 11.2 Internal scroll — wide tables inside a bounded container

A wide table causes page-level horizontal scroll unless something contains it. The kit's answer is one pattern, used verbatim in its own call sites (`src/components/ui/data-table.tsx`, `src/components/admin/UserTable.tsx`): the low-level `Table` (§1.2) renders its own card and a `<table className="w-full min-w-125">` (31.25rem) but **no scroller**, so the caller — always **inside a parent card** (`DataTable`'s own, or the page card in `UserTable`) — wraps it in a plain scrolling box and flattens `Table`'s card with `className="surface-flat rounded-none"`, so the parent card draws the bounds and the box only scrolls:

```tsx
<div className="scrollbar-visible overflow-x-auto">
  <Table columns={columns} data={rows} keyExtractor={(r) => r.id} className="surface-flat rounded-none" />
</div>
```

`DataTable` (§1.1) already does exactly this inside its card — never wrap a `DataTable` in a second scroller or give it a `min-w-*`: its `className` lands on the outer card, and the whole card (header, toolbar, pagination) would scroll.

| Class                        | Why it matters                                                                                  |
| ---------------------------- | ----------------------------------------------------------------------------------------------- |
| `overflow-x-auto`            | Enables horizontal scroll on the wrapper                                                        |
| `scrollbar-visible`          | The kit's thin, token-colored scrollbar (`src/app/globals.css`): thumb always visible, stronger on hover |
| `surface-flat rounded-none`  | Flattens `Table`'s own card so the parent card draws the bounds — no double border                 |
| `min-w-125`                  | Already on the `<table>` — the minimum width that triggers the scroll                            |

For wide content that is **not** a kit table (a third-party grid, a wide `<pre>`, a chart with a fixed minimum width) use the same wrapper with `rounded-xl border` and put the `min-w-*` on the inner block.

**Anti-patterns:** `overflow-x-hidden` (truncates data), `whitespace-nowrap truncate` on every cell (data loss). Scroll the container, not the cell.

### 11.3 Mobile-wrapping tabs

Tabs must wrap at 375px when they don't fit inline. Override the fixed height so multi-row triggers stay touch-friendly:

```tsx
<Tabs defaultValue="datos" className="w-full">
  <TabsList className="h-auto! w-full flex-wrap p-1.5">
    <TabsTrigger value="datos" className="h-auto py-2.5"><User className="h-4 w-4" /> Datos</TabsTrigger>
    <TabsTrigger value="actividad" className="h-auto py-2.5"><Activity className="h-4 w-4" /> Actividad</TabsTrigger>
  </TabsList>
  <TabsContent value="datos"><EntityDataTab /></TabsContent>
</Tabs>
```

`w-full` spans the container · `h-auto! flex-wrap` allows multi-row · `h-auto py-2.5` gives each trigger a taller touch target.

### 11.4 Scroll-lock + `scrollbar-gutter` — the Radix viewport shift on Windows/Linux

Two scrollbar strategies clash: `scrollbar-gutter: stable` on `html` (in `globals.css`, reserves the scrollbar space so page height never causes a layout jump) and `react-remove-scroll-bar`, which every Radix primitive with modal scroll-lock mounts (`Dialog`, `AlertDialog`, `Sheet`, `DropdownMenu`, `Popover` with `modal`, and `Select` unconditionally via `RemoveScroll`). The library measures `gap = innerWidth - clientWidth` and injects `body[data-scroll-locked] { margin-right: <gap>px !important }` to compensate a scrollbar that, with the gutter reserved, never disappeared — a double offset of ~10-17px each time one of them opens. macOS uses overlay scrollbars (`gap = 0`), so the bug is invisible there.

The kit ships the fix in `globals.css`; **don't remove it**:

```css
html body[data-scroll-locked] {
  margin-right: 0 !important;
  --removed-body-scroll-bar-size: 0px !important;
}
```

The `html body[...]` selector wins on specificity over the library's runtime `<style>` (equal specificity + `!important` on both sides would let cascade order hand the win to the library, which mounts later). Dropping `scrollbar-gutter: stable` instead would bring back the page-height jump. **Validate from macOS:** `System Settings → Appearance → Show scrollbars: Always`, open a `Select`, and check `getComputedStyle(document.body).marginRight` is `0px` while `data-scroll-locked` is on `<body>`.

### 11.5 Form layout — elevated card + 2-column grid

One elevated card per logical section (`Datos generales`, `Permisos`, …), `md:grid-cols-2` for paired fields collapsing to one column on mobile, long inputs full-width via `md:col-span-2`, and the actions outside the card, right-aligned. The card wrapper is the kit's `surface-raised` utility (`sk-tokens-neomorphism`); never stack raised-on-raised — break into siblings with `space-y-6`.

```tsx
const form = useForm({ schema, defaultValues }); // the kit's hook wires the Zod resolver (§2.1)

<Form form={form} onSubmit={onSubmit} className="space-y-6">
  <div className="surface-raised rounded-xl p-6">
    <h3 className="text-foreground mb-4 font-semibold">Datos generales</h3>
    <div className="grid gap-6 md:grid-cols-2">
      <FormField name="name" label="Nombre" />
      <FormField name="email" label="Email" type="email" />
    </div>
  </div>
  <div className="flex items-center justify-end gap-3">
    <Button type="button" variant="outline" size="lg">Cancelar</Button>
    <SubmitButton className="w-auto px-6">Guardar</SubmitButton>
  </div>
</Form>
```

## 12. URL state & skeletons

### 12.1 URL state — the cheapest persistent store

Anything **bookmarkable or shareable** lives in the URL, not in client state: filters, pagination, sort, search, the active tab. It survives refresh, works with back/forward and deep-links. Client state (`useState`) is for the ephemeral: dialog open, hover, focus, controlled inputs before submit.

- **Tables:** `useTableState` / `useServerTableState` (§1.5) already sync `?sort=&dir=&page=&limit=` — never re-implement that. Canonical names → `project/reference/HOOKS.md`.
- **Anything else** (`?tab=security`, `?region=eu`): read with `useSearchParams()` and write with `router.push(`${pathname}?${params}`, { scroll: false })`, deleting the key when the value is empty. Keep it file-local — the kit ships no generic query-state hook, and citing one by a name that `HOOKS.md` does not list is exactly the drift that registry exists to prevent.

### 12.2 Skeleton mirrors the real layout

A `loading.tsx` / `Suspense` fallback must mirror the **final layout's dimensions** — same row heights, same gaps — or the real content lands with a layout shift. A generic spinner on a data-heavy page reads as slower than a correctly-sized skeleton.

```tsx
export function UserListSkeleton() {
  return (
    <div className="space-y-4">
      {Array.from({ length: 5 }).map((_, i) => (
        <div key={i} className="flex items-center gap-4">
          <Skeleton className="h-12 w-12 rounded-full" />
          <div className="space-y-2">
            <Skeleton className="h-4 w-40" />
            <Skeleton className="h-4 w-36" />
          </div>
        </div>
      ))}
    </div>
  );
}
```

`Skeleton` (§5.5) is a kit-authored component that lives in `ui/` — it declares its own `SkeletonProps` (`SK.md §3.3`), so it may be extended; the row shape is yours.

## 13. Accessibility checklist

- [ ] `<img>` has `alt` (empty `alt=""` for decorative images)
- [ ] Every input has an associated `<label htmlFor>` or `aria-label` (the form kit's `FormField` does this for you)
- [ ] Interactive elements are `<button>`, not `<div onClick>`; navigation uses `<Link>`, not `router.push` on a div
- [ ] `focus-visible` ring on every interactive element (keyboard users)
- [ ] Contrast meets WCAG AA (4.5:1 text, 3:1 large text / UI) — measured by the evidence harness, not asserted
- [ ] Keyboard navigation works end-to-end (Tab, Shift+Tab, Enter, Space, Esc); row-clickable tables also handle `tabIndex={0}` + Enter/Space
- [ ] Dialogs trap focus and restore it on close (`ConfirmDialog` / `Dialog` already do)
- [ ] Live regions (`role="alert"`, `aria-live`) announce async errors
- [ ] Icon-only buttons have `aria-label` or a tooltip with visible text
